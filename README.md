д# MCOC Vision

Система локального распознавания противника из OBS Virtual Camera или видео.
Первая версия: GPU-детектор, привязка противника между кадрами, измерение скорости.
Распознавание атак пока не реализовано. Готовые веса COCO — исходная точка, а не
обученная на MCOC модель. Устойчивость на всех персонажах пока не подтверждена.

## Установка и запуск (Windows / PowerShell)

```powershell
./setup.ps1
./.venv/Scripts/python.exe main.py cameras
./.venv/Scripts/python.exe main.py probe --source obs --seconds 10
./.venv/Scripts/python.exe main.py run --source obs --candidates
```

Для проверки открытого детектора по текстовым подсказкам:

```powershell
./.venv/Scripts/python.exe main.py run --source obs --model models/yolov8s-worldv2.pt --prompts "video game fighter" superhero "human character" person
```

Запустите виртуальную камеру в OBS. `--source obs` выбирает устройство по имени,
не угадывает индекс 0. Для другого устройства укажите индекс из `cameras`.
Запускайте из корня проекта. Первая загрузка PyTorch занимает около 3 ГБ;
при первом запуске детектора скачиваются стандартные веса YOLO11n.
Нужен Python 3.11 и NVIDIA-драйвер с поддержкой выбранной CUDA 12.6.
Системный CUDA Toolkit для PyTorch-wheel не требуется.

Режим без окна, ограниченный по времени:

```powershell
./.venv/Scripts/python.exe main.py run --headless --seconds 30 --report artifacts/benchmark.json
./.venv/Scripts/python.exe main.py run --source 'D:/Videos/fight.mp4'
```

Сбор небольшой разнообразной выборки кадров без записи всего видео:

```powershell
./.venv/Scripts/python.exe main.py collect --source obs --seconds 300 --output artifacts/collected
```

Прямой захват видимого окна игры без OBS:

```powershell
./.venv/Scripts/python.exe main.py probe --source screen --window Champions --seconds 10 --snapshot artifacts/direct-screen.png
./.venv/Scripts/python.exe main.py collect --source screen --window Champions --seconds 300 --output artifacts/collected-direct
./.venv/Scripts/python.exe main.py run --source screen --window Champions --model models/yolov8s-worldv2.pt --prompts "video game fighter" superhero "human character" person
```

Окно должно быть видимо и не свёрнуто. Программа сама находит его клиентскую
область и монитор, включая монитор с отрицательными координатами. Захват использует
Windows Desktop Duplication через DXcam; OBS при этом не нужен. Если другое окно
закрывает игру, DXGI захватит перекрытие, поэтому для сбора данных окно игры лучше
держать открытым целиком.

Сборщик проверяет кадр каждые 0,5 секунды, отбрасывает близкие дубли и всё равно
сохраняет контрольный кадр не реже одного раза в 2 секунды. Сырые изображения и
`manifest.json` остаются локально. Это материал для проверки и последующей разметки,
а не автоматически истинные метки.

Предварительная разметка существующей выборки:

```powershell
./.venv/Scripts/python.exe main.py prelabel --input artifacts/collected-live --output artifacts/prelabels-live
```

Рамки записываются в `labels_suggested`, а их изображения для просмотра — в
`previews`. Эти метки намеренно отделены от обучающего датасета и имеют статус
`needs_review`: до ручной проверки использовать их для обучения нельзя.

Локальная проверка предложенных рамок:

```powershell
./.venv/Scripts/python.exe main.py review --input artifacts/prelabels-live
```

Левая кнопка и протягивание добавляют рамку, правая кнопка внутри рамки удаляет её.
`Space` подтверждает кадр и открывает следующий, `B` возвращает предыдущий, `C`
очищает рамки, `R` возвращает исходные предложения, `Q` сохраняет прогресс и выходит.
Подтверждённые метки записываются отдельно в `labels_reviewed`.

Видео воспроизводится с исходной частотой; при перегрузке анализируется свежий кадр.
В окне: `Q`/`Esc` — выход, `R` — повторный захват противника справа,
`D` — рамки всех кандидатов, `S` — сохранить сырой кадр локально для разметки.
Зелёная рамка подтверждена детектором, оранжевая — краткий прогноз/неоднозначность.
`lost` означает потерю: старую рамку система не держит бесконечно.
Если изображение старше 250 мс после получения приложением, рамки скрываются
и появляется `STALE SOURCE`. Замёрзший upstream-поток с повторяющимися кадрами
эта проверка не распознаёт: для этого нужен отдельный тест свежести источника.

## Автоматическая сессия боёв

Первый рабочий вариант автоматически находит боевой HUD, записывает каждый бой в
отдельную папку и после его окончания ставит кадры в фоновую очередь разметки:

```powershell
.\.venv\Scripts\python.exe main.py session --source screen --window Champions --player juggernaut
```

Или коротким запускным скриптом:

```powershell
.\start-session.ps1
```

Если слева во всех боях один герой, его можно указать через `-Player juggernaut`.
Если герои меняются внутри серии, параметр не нужен: личности подтверждаются
отдельно для каждого завершённого боя.

Запускайте сессию, пока на английском экране игры открыта установленная очередь.
Первый полученный кадр сохраняется в `data/sessions/<session>/queue_screen.jpg`.
Встроенный OCR Windows читает шесть фиксированных строк и сохраняет три пары в
`lineup.json`; строки 1–3 назначаются боям 1–3. Имена остаются доступными для
проверки перед окончательным экспортом.

Остановка — `Ctrl+C`; текущий бой сохраняется как частичный. Окно предпросмотра
не создаётся. Кадры и манифесты находятся в `data/fights`, состояние фоновых
задач — в `data/jobs`, неизвестные соперники — в `data/unresolved`. Для указанного
слева персонажа создаётся индекс в `data/characters/<имя>/pending` с преобразованием
`flip_horizontal`: сами изображения и исправляемые метки не дублируются.

Детектор бойцов выполняется только после завершения боя в отдельном потоке. Если
на конкретном ПК это влияет на FPS следующего боя, запустить с `--defer-labeling`:

```powershell
.\.venv\Scripts\python.exe main.py session --source screen --window Champions --player juggernaut --defer-labeling
```

В текущей версии имя левого персонажа задаётся один раз на сессию. Правый портрет
и верхняя часть HUD сохраняются для следующего модуля визуальной идентификации;
пока имя нельзя подтвердить, бой остаётся `unresolved`, а не получает ошибочную
метку. Предложенные рамки имеют статус `needs_review` и автоматически не становятся
обучающей истиной.

После фоновой обработки открыть последний бой для проверки рамок:

```powershell
.\.venv\Scripts\python.exe main.py review-fight
```

После проверки весь бой подтверждается одной командой. Имена указывают исходные
стороны кадра; весь бой целиком получает один split:

```powershell
.\.venv\Scripts\python.exe main.py confirm-fight --fight-id ID --left juggernaut --right hulk --split train
```

Для честной проверки новой пары, которой не было в обучении:

```powershell
.\.venv\Scripts\python.exe main.py confirm-fight --fight-id ID --left spider_man --right hulk --split test
```

Одна и та же пара не может попасть в разные split. В `data/detector` полный кадр
хранится с двумя рамками одного класса `fighter`. В `data/characters/<герой>`
хранится полноразмерное персональное представление: целевой герой — класс 0,
второй видимый боец — класс 1; левое представление отражается целиком.

Добавить единственный статичный эталон аватара:

```powershell
.\.venv\Scripts\python.exe main.py avatar-add --character hulk --image path\to\hulk.png
```

## Архитектура и ограничения

- Поток захвата постоянно читает устройство. Один заменяемый слот хранит последний
  кадр; очереди кадров приложения нет. Настройка буфера драйвером может игнорироваться,
  её результат записывается в отчёт.
- Поток распознавания выполняет YOLO на CUDA FP16 с batch=1. При отсутствии CUDA
  выполнение завершается понятной ошибкой, без незаметного перехода на CPU.
- Трекер использует геометрию, скорость и сопоставление рамок. Для начала нужны
  два уверенно обнаруженных, разделённых бойца в трёх последовательных обработанных
  кадрах. Правый считается противником. После этого выбирается согласованный
  с предыдущей траекторией кандидат, а не просто самая правая рамка.
- Прогноз без подтверждения виден не более 120 мс. После 600 мс потери трек
  сбрасывается; новый захват получает новый ID. Перекрытия, резкая смена сцены,
  перестановка сторон и пропуски детектора могут нарушать идентичность.
  Гарантированная re-identification пока не реализована. `R` помогает явно сбросить
  неверный захват после смены боя.
- Интерфейс показывает рамку на том самом кадре, который был обработан. Перенос
  рамки на более новый кадр без коррекции движения не выполняется.
- `Frame` хранит номер, монотонную временную метку получения и, для файла,
  позицию по времени; `Track` — ID, состояние, рамку и время без наблюдения.
  Эти структуры можно использовать для будущего распознавания действий.
- В живом цикле нет видеозаписи, сетевого сервиса или выгрузки кадров в облако.
  Диагностические PNG и JSON остаются в `artifacts/`; автоматическая запись боёв
  не включена.

## Как интерпретировать измерения

`capture_delivery_fps` — частота доставки кадров API, включая возможные дубликаты.
`inference_fps` — обработанные кадры в секунду после прогрева; FPS игры отдельно
не измеряется. `skipped_for_freshness` — кадры, пропущенные ради свежести.
`detector_ms` включает препроцессинг, модель, постобработку и получение рамок CPU.
`application_ms` — от возврата `read()` до готового результата. p50/p95/p99
считаются по последним 3600 результатам. `read->display` измеряется до вызова
отрисовки и не включает фактический вывод монитором.

**Ни одна из этих величин не измеряет задержку игра → OBS → драйвер.**
`source_to_result_latency_ms` намеренно имеет значение null. Нужен отдельный тест
с визуальным таймером/счётчиком на источнике. FPS захвата нельзя подменять числом
перерисовок окна. Доля кадров с рамкой не является точностью распознавания.

Для проверки на боях фиксируем потерю рамки, ошибочный захват нашего персонажа,
ошибки размера/положения рамки и задержку восстановления. Сравниваем FPS игры/OBS
без программы и с программой при одинаковой сцене и настройках.

## Дообучение под игру

Размечать **обоих бойцов одним классом `fighter`**. Роль противника назначается
трекером, а не внешностью персонажа. Разделение train/val/test — целыми боями,
не соседними кадрами. Для проверки обобщения нужны отдельные персонажи и арены
в тестовой части. Рамка охватывает видимое тело и экипировку по единому правилу;
вспышки, числа урона и отдельные снаряды не включаются в рамку тела.

Формат YOLO: `images/train/*.png` и `labels/train/*.txt` (аналогично val/test).
В каждой строке метки: `0 cx cy width height`, значения нормированы на размер кадра.
Пример описания: `configs/fighters.example.yaml`. Сначала проверьте разметку вручную.

```powershell
./.venv/Scripts/python.exe main.py train --data datasets/mcoc/data.yaml --batch 8
./.venv/Scripts/python.exe main.py run --model runs/train/fighters/weights/best.pt
```

Батч 8 — начальная настройка; если не хватает VRAM, снизьте до 4. Обучение
не следует запускать одновременно с проверкой задержки игры. Датасета в репозитории
пока нет; команда обучения не создаёт и не подменяет реальные метки автоматически.

## TensorRT (следующий измеряемый шаг)

Первичная версия работает через CUDA PyTorch. TensorRT — дополнительный backend,
а не условие запуска. После выбора модели установить совместимую с драйвером
и Windows версию TensorRT по документации NVIDIA, затем:

```powershell
./.venv/Scripts/python.exe main.py export --model models/yolo11n.pt
./.venv/Scripts/python.exe main.py run --model models/yolo11n.engine
```

Engine собирается для конкретного GPU/окружения с фиксированным размером и batch=1.
После экспорта сравнить качество рамок и p95 с исходными весами на одних боях.
Нельзя переносить обещания скорости из чужих бенчмарков. INT8 пока не используется.

## Проверки

```powershell
./.venv/Scripts/python.exe -m pytest -q
```

Тесты покрывают пропуск очереди при медленном потребителе, освобождение камеры,
выбор правого бойца, ограничение прогноза, неоднозначность и ID повторного захвата.
Это проверки логики, не доказательство качества детектора на игре.

Документация зависимостей: [YOLO11](https://docs.ultralytics.com/models/yolo11/),
[PyTorch wheels](https://docs.pytorch.org/get-started/previous-versions/),
[TensorRT](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/best-practices.html).
Ultralytics распространяется на условиях AGPL-3.0 / Enterprise; учесть это при
будущем выборе способа распространения проекта.
