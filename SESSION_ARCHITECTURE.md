# Непрерывные сессии сбора данных

Статус: спецификация следующего этапа. Текущий `run --hard-samples`
сохраняет отдельные кадры; описанный ниже менеджер сессий ещё не реализован.

## Цель

Один ручной запуск сессии, автоматическое выделение отдельных боёв,
накопление примеров обоих бойцов и повторное использование исправлений.
Работа только с пикселями экрана; правила AGENTS.md сохраняются.

## Хранилище

```text
data/
  sessions/<session_id>/session.json
  fights/<fight_id>/
    fight.json
    frames/
    annotations/suggested/<model_version>/
    annotations/reviewed/
  characters/<character_id>/
    character.json
    samples/<sample_id>.json
  unresolved/<fight_id>.json
  jobs/<job_id>.json
  releases/<dataset_version>/manifest.json
```

Бой — первичный источник. Папки персонажей содержат ссылки-записи на кадры,
рамки и преобразования, а не независимые копии исправляемых меток.
Каждый sample хранит fight_id, frame_id, object_id, исходную сторону,
character_id, уверенность идентификации, происхождение рамки,
версию модели, статус проверки и transform (`identity` или `flip_horizontal`).
Исправление одной исходной рамки автоматически учитывается во всех представлениях.
Идентификаторы уникальны между запусками. Существующие сессии не перезаписываются.

## Два персонажа из одного боя

Для правого бойца создаётся обычное представление. Для левого создаётся
зеркальное представление, где он расположен справа. Преобразование рамки:
для YOLO `cx' = 1 - cx`, `cy`, `width`, `height` остаются прежними.
Для пиксельных границ `[x1, y1, x2, y2]`: `[W-x2, y1, W-x1, y2]`.

Персонаж является метаданными; детектор продолжает учить общий класс `fighter`.
В полном изображении должны оставаться метки ОБОИХ видимых бойцов.
Полный кадр с меткой только Халка научил бы модель считать Джаггернаута фоном.
Выбор целевого персонажа хранится отдельно. Изолированные обрезки и маски
можно формировать позднее для анализа действий; обрезка не заменяет полнокадровые
примеры детекции.

Зеркальные варианты создаются при экспорте или загрузке обучающего набора.
Оригинал и все производные всегда принадлежат одному разделу train/val/test.
Разделение производится целыми боями, с отдельной проверкой новых персонажей.

## Распознавание состояния экрана

Независимый от детектора бойцов модуль выдаёт состояния:
`unknown`, `menu`, `loading`, `intro`, `combat`, `paused`, `result`.
Он использует элементы интерфейса, распознавание текста и короткую историю
наблюдений. Отсутствие рамок бойцов само по себе НЕ завершает бой.
Падение, оглушение, перекрытие и спецатаки должны оставаться внутри боя.

Начало подтверждается последовательностью наблюдений, сохраняется короткий
буфер предшествующих кадров. Пауза приостанавливает сбор, но не создаёт новый бой.
Результат или подтверждённый переход из боя закрывает запись. Неуверенный
переход сохраняется для диагностики, а не автоматически размечается как бой.
Пороговые времена подбираются по сохранённым последовательностям.

Ограничение 30–60 секунд действует на один фрагмент сохранения. Длинный бой
может иметь несколько фрагментов с одним fight_id; лимит первого боя не должен
блокировать дальнейшую сессию. Завершение сессии закрывает незавершённый бой
с признаком `partial`, пригодным для дальнейшего анализа.

## Идентификация персонажей

Использовать экран подбора/входа в бой, имена там, где они присутствуют,
и портреты бойцов. В текущих изображениях слева над здоровьем — ник игрока,
поэтому OCR этого поля не определяет левого персонажа.
Решение подтверждается несколькими кадрами и согласованием портрета с текстом.
Каталог хранит постоянный character_id и варианты отображаемых имён/портретов.
Низкая уверенность направляет бой в unresolved. Одно уточнение пользователем
назначает персонажа всему треку боя; сомнительное имя не создаёт автоматически
новую подтверждённую папку героя.

## Параллельность и восстановление

Захват и лёгкое определение состояния экрана работают независимо от обработчика
завершённых боёв. Запись использует ограниченную очередь с явным учётом потерь.
Обработчик получает задания с диска: идентификация, предложения рамок,
временное сопровождение, выбор разнообразных примеров и индексация персонажей.
Статусы заданий: pending, running, completed, failed; после перезапуска
незавершённые задания доступны для повторной обработки.
Повторная обработка не создаёт дубликаты samples и не меняет reviewed-метки.

GPU общий с игрой. Фоновая обработка имеет ограничение нагрузки и может
приостанавливаться при росте задержки. Возможность параллельной работы не означает
гарантию отсутствия просадки FPS: бюджет проверяется измерениями. Задания могут
накапливаться до конца игровой сессии. Обучение запускается отдельно.
В интерфейсе видны активный бой, объём записи, очередь, заполнение диска и ошибки.
При лимите диска запись явно приостанавливается; старые данные не удаляются молча.

## Разметка и обучение

Автоматические рамки остаются suggested. Согласие детектора и сопровождения
помогает отбору, но не гарантирует правильность: ошибки могут быть общими.
Первый этап использует проверенные человеком рамки для обучения. Автоматические
метки подключаются только после измерения качества на независимой выборке.
Выборка для проверки содержит сложные кадры, разнообразные позы и небольшую
случайную долю уверенных предсказаний, чтобы обнаруживать уверенные ошибки.

Каждый выпуск датасета фиксирует источники и версии меток. Новая модель учится
на новых исправлениях и старых примерах. Тестовый набор не используется для
обучения. Выпуск модели требует сравнения пропусков, ложных рамок, точности
границ, устойчивости и задержки. Рабочая версия не меняется посреди боя.

## Проверяемые этапы реализации

1. Хранилище боёв и персонажей, уникальные ID, журнал заданий, экспорт двух сторон.
   Проверка повторного импорта, зеркальных меток и сохранности ручных правок.
2. Определение состояния экрана на локальных последовательностях с загрузкой,
   паузой, результатом, атаками и падениями. Проверка ложных границ боёв.
3. Определение имён/портретов и очередь неуверенных идентификаций.
4. Команда/кнопка сессии, отдельный фоновый обработчик, восстановление после сбоя,
   измерение нагрузки в игре пользователем.
5. Очередь проверки и версионированное обучение с сохранением старых навыков.

Текущие разреженные 240 кадров полезны для прототипа классификации состояний,
но недостаточны для доказательства надёжного определения границ длительной сессии.
Для этого нужны последовательности переходов между боями.
